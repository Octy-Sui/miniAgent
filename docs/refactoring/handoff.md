# 给后续执行模型的启动与交接说明

## 可直接复制的启动提示词

```text
在 miniAgent 仓库执行 docs/refactoring/plan.md 中的重构方案。

先读 AGENTS.md、docs/refactoring/plan.md、progress.md，再读取当前任务卡和
architecture.md 对应章节。不要依赖历史对话；不要继续旧 docs/HANDOFF.md 的任务。

项目未上线，不需要旧数据/旧导入路径/字段兼容，不写迁移器、alias 或双写逻辑。
也不要删除用户现有数据库；验证用临时目录和新库。

按 tasks.md 顺序一次完成一张卡，先检查工作树与前置任务证据。
开始前把卡标 ACTIVE，完成并验证后标 DONE；不能仅凭代码看起来正确标 DONE。
小步修改定义、直接消费者和测试，保持每卡结束时可导入、可验证。

保留事务、审批、取消和先提交后发布的不变量；不新增预算、跨进程恢复、完整
Trace 导出、新工具或新评估器。不修改 README，不自动 commit/push，不运行真实模型。

上下文不足时，先把具体文件、函数、验证、失败原因和下一动作写入 progress.md，
再按 handoff.md 模板交接。新会话先核对实际 diff，再续作 ACTIVE 卡，不重做 DONE 卡。

这次先执行当前第一个可执行任务；结束时报告本卡结果、验证和下一任务。
```

如果希望连续执行，可把最后一句改为：“连续执行可执行任务，每卡验收和落盘后再进入下一卡；遇到真实阻塞或上下文不足时按交接协议处理。”不要把“持续执行”理解为可以跳过任务门禁。

## 中断前必须写入 progress 的交接信息

```text
当前任务：
当前子步：
当前 HEAD：
工作树文件归属：
最后一个已验收任务：

已完成的具体改动：
尚未完成的调用方/类型/SQL：
当前代码是否能导入：
运行过的测试及真实结果：
尚未运行的验证：

当前唯一需要解决的问题：
复现命令：
已排除的原因：
下一条具体操作：
继续前必读的 3—6 个文件：
不得回退的行为/决定：
完成当前卡的剩余清单：
```

交接记录写在 progress 中，不另建多个相互矛盾的“最新状态”文件。代码中可以有短期未完成工作，但必须写出实际缺口，不能遗留无说明的 pass/TODO 或把类型错误标为“后续统一处理”。

## 新会话恢复流程

1. 检查 HEAD、git status 与 progress 记录是否一致；不同则先查看 diff，保留他人改动。
2. ACTIVE 卡优先续接；若表中 TODO 但代码已部分完成，核对后补记，不能盲目重复生成文件。
3. 读取当前卡、architecture 对应契约及交接列出的代码。
4. 先复现最后一个失败或确认最后检查点，避免无依据地把全部测试再跑一遍。
5. 完成当前子步，再运行该卡规定的验证；没有新变化不反复扩大测试。
6. 更新任务状态、命令结果和下一动作，然后再继续下一卡。

## 防止长任务失控的约束

- 一个会话不必读所有 20 张卡；但必须知道当前卡的依赖和边界。
- 不为“看起来更整齐”提前迁移下一阶段文件；普通 import 更新除外。
- 不把方案中的未来文件视为必建空壳，尤其 budget.py、Jinja 模板和完整 Trace 投影。
- 已有测试失败先判断是否基线问题，不直接改 expected 值迁就实现。
- 不用删除存储、删历史测试或禁用验证解决结构变化。
- 涉及取消、审批 CAS、事件连续性时，保留证据再优化，不以文件变短作为完成标准。
- 一旦实际设计需要偏离本方案，在 progress 写原因与影响；影响产品语义的变更需用户决定，普通实现选择可按约束自行完成。
