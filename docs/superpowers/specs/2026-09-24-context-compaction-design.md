# Context Compaction Feature Requirements

## 1. 目的与范围

MiniAgent 的长任务会持续累积模型消息。当前 Runtime 在每个 Step 将 `RunState.conversation.messages` 全量发送给 Provider，尚无上下文容量管理。此功能要同时达到三个目标：

1. 长任务接近模型上下文上限时，自动压缩旧上下文并继续同一 Run。
2. 对可比较的长任务，计入压缩调用后仍减少总计费 token。
3. 持久化压缩后的可续行状态，定义未来跨进程恢复读取该状态的契约。

首版交付对象是当前 Qwen Provider。Runtime 与 Provider 的边界应允许未来接入其他 Provider，首版不依赖任何 Provider 原生压缩接口。启用持久化存储的 Run 须满足全部三个目标；无存储的 Run 仍可在进程内压缩续行，但不具备跨会话恢复保证。跨进程恢复入口、手动压缩命令、跨 Run 长期记忆和策略插件不在本次范围内。

## 2. 用户可见行为

### FR-1 自动触发与续行

- Runtime 在准备下一次模型请求的安全边界，按目标模型的可用上下文预算评估预计输入，并为模型输出保留容量。
- 当预计输入达到可配置触发阈值时，Runtime 在发送下一次请求前压缩已完成的旧 Step。系统指令、原始任务和最近若干完整 Step 保持原文。工具调用与对应结果不得拆开。
- 压缩成功后，下一次请求使用“固定指令与原始任务＋摘要＋近期原文”，继续原 Run、原 Agent 和原 Step 上限。压缩本身不算 Step，也不执行工具或改变审批决定。
- 若没有可压缩的完整旧 Step，Runtime 不得删除近期消息以伪造容量；它应按 FR-6 给出明确结果。
- 默认预算、触发阈值、压缩后目标大小及近期原文保留量应可配置，并随 Run 定义持久化。模型上下文容量未知时，配置必须提供容量，不能将未知视为无限。

### FR-2 摘要内容与质量

- 摘要覆盖被替换的旧消息，至少保留任务目标、用户硬约束、已完成工作、关键观察与其来源、尚未解决的问题、失败或被否定的尝试、下一步动作。
- 摘要须区分已验证事实与推断；来源应能回指 Run 内的历史边界或具体事件。未能核实的内容不得写成已验证事实。
- 对后续执行仍有用但无法准确概括的内容，保留其原文或可读取的引用。摘要不得成为工具结果、审批、策略判断或 Workspace 状态的权威记录。
- Runtime 在发布摘要前校验其非空、必要字段齐全、与近期原文组合后低于目标预算，并且不会产生孤立的工具调用或工具结果。校验失败视为未压缩。

### FR-3 成本与用量

- 压缩调用遵循 Run 的取消和超时控制；其输入、输出、缓存用量及费用计入 Run 总用量，并在观测数据中单独标识用途。
- 同一来源边界不得因普通续行而重复压缩。再次压缩时可包含上一版摘要，但必须记录新旧压缩版本的关系。
- 触发策略应避免对短任务和预计无法回收压缩成本的任务做非必要压缩；接近容量上限时，续行优先于单次压缩的成本回收。

## 3. 状态、Snapshot 与恢复契约

### FR-4 压缩状态

Runtime 将发给模型的活动上下文与 Run 的原始执行事实区分。每个压缩版本记录：来源 Run 与历史边界、压缩前 Snapshot 版本、被覆盖的旧消息范围、保留的原文范围、摘要及其来源、模型身份、预算估计与实际用量、前一压缩版本。原始任务和系统指令始终来自 Run 定义，不能只依赖摘要副本。

现有不可变 Snapshot 保存完整 `RunState` 和恢复上下文。压缩前 Snapshot 保留被替换的原文；压缩后 Snapshot 保存新的活动上下文。为使原文可审计，存储契约须支持按版本读取被引用的历史 Snapshot，并保证这些版本在相应 Run 的保留期内不被清理。无需为首版另建独立的摘要存储系统。

### FR-5 发布时点与原子性

- 仅在安全边界压缩：待压缩的 Step 已完成，不能存在未配对的工具调用或待决审批。
- 摘要生成并通过校验后，**立即触发一次 Snapshot 提交**。新活动上下文、压缩元数据、压缩完成事件和新 Snapshot 必须通过现有 Run 提交机制在同一数据库事务中生效；不等待下一 Step 完成。
- 提交成功前，旧活动上下文仍是唯一已发布版本；提交成功后，Runtime 才使用新版发起后续模型请求。数据库提交失败不得使用未提交摘要。
- 未来恢复流程以最后一版已提交的 Run 状态和 Snapshot 为准，校验 Snapshot 的 Run ID、事件序列、版本及引用完整性，重建与提交时相同的下一次模型输入。已提交摘要不得在恢复时自动重新生成。
- 发起压缩前记录请求事件，成功或失败后记录用量与结果。压缩调用已完成但结果提交前发生进程中断时，未来恢复可能重复付费生成摘要；请求事件可标识未完成的尝试，但无法保证获知 Provider 已计费的确切用量。跨进程恢复执行器属于后续功能。

## 4. 错误与边界条件

### FR-6 失败处理

- Provider 可恢复错误可有限重试；取消须立即停止压缩。重试次数和超时受配置上限约束，不得形成无限压缩循环。
- 摘要为空、未通过必要信息校验、压缩后仍超预算、没有可压缩历史或提交失败时，不发布新压缩版本，并记录可区分的失败原因。
- 摘要生成或校验失败时，若旧上下文仍在安全预算内，则继续使用旧版；否则以明确的上下文容量或压缩失败原因结束 Run。不得静默删减原文。持久化提交失败按现有 Run 存储失败处理，不继续发起模型请求。
- 如果 Provider 对原先预计可容纳的请求返回上下文超限错误，Runtime 可在安全边界强制尝试一次压缩并重试同一模型请求；仍失败则终止，且不得重复执行已经完成的工具调用。
- 压缩摘要中的文本视为历史材料，不得改变更高优先级的指令、工具许可或审批状态。

## 5. 验收

使用版本固定的长任务集合、相同模型配置及可重复的评价合同。容量与成本使用不同样本组，避免把无法完成的未压缩任务用于成本比较。

| 目标 | 验收条件 |
| --- | --- |
| 续行 | 容量组包含未压缩时会越过配置上下文预算的任务；压缩后可继续并完成任务。Runtime 不发送按其预算估计已超限的请求；Provider 实际拒绝时执行 FR-6 的一次性兜底。 |
| 成本 | 在压缩与未压缩均能完成的成本组中，计入所有压缩调用后，压缩组总计费 token 的中位数至少降低 20%，任务通过率不低于未压缩组。 |
| 恢复契约 | 压缩提交后的最新 Snapshot 重新加载后构造的下一次模型输入与提交时相同；模拟摘要生成、数据库提交和提交后中断，压缩状态、事件与 Snapshot 均不会部分生效。 |
| 摘要质量 | 对固定样本核查原始目标、硬约束、未完成工作、关键证据及来源，不允许关键遗漏或把未验证推断写成事实。 |
| 执行安全 | 工具调用与结果保持配对；压缩不改变 Step 数、待决审批、工具执行结果或 Workspace 状态。 |

对容量组与成本组分别保存任务版本、模型版本、配置、样本结果和 token 用量，以便复现比较。通过率门槛按同一固定集合的成功任务数判定。

正式验收前须冻结逐任务评价合同：输入及初始 Workspace 修订、允许的最终文件或外部状态、独立于 Agent 结束语的成功／失败判定、判分命令或人工检查步骤，以及失败和缺失产物的处理。容量组与成本组均按该合同逐 Run 判分，保留最终 Workspace 差异和判定记录；Agent 自述不能作为任务完成的依据。成本组另须冻结每任务每臂重复次数、全部计划 Run 的纳入规则和中位数计算口径，运行后不得删除失败样本或以补跑替换。五项条件均须由非实现者按预先冻结的证据清单复核；未冻结的摘要语义审阅材料不能判为通过。

## 6. 参考与设计取舍

Anthropic 的按需压缩将旧对话替换为可供后续请求使用的摘要；OpenAI Responses 同时提供自动阈值压缩和显式压缩，显式压缩返回下一轮使用的上下文窗口。这些资料支持“阈值触发、保留可续行上下文”的产品方向，但首版采用 Runtime 管理的文本摘要，以适配当前 Qwen Provider。
