测试依据是 [功能需求](2026-09-24-context-compaction-design.md)、[架构设计](2026-09-24-context-compaction-architecture-design.md) 和[测试分析](2026-09-29-context-compaction-test-analysis.md)。以下是**待实施的黑盒测试设计**，不是已执行结果。

## 测试单元划分

| 单元 | 来源 | 主要逻辑 | 技术 | 选择原因 |
| --- | --- | --- | --- | --- |
| U1 | FR-1、FR-6、架构 §3/§5/§7 | 按模型读取配置并拒绝无效配置 | 等价类＋边界值 | 配置查找是类别问题，容量、比例与重试配置有数值边界 |
| U2 | FR-1、FR-2、FR-3、FR-6、架构 §5 | 软触发、硬阻断、摘要请求容量与压缩结果 | 决策表＋边界值 | 多条件共同决定是否压缩、续行或失败；摘要请求有独立的容量上限 |
| U3 | FR-1、FR-5 | 安全边界、完整 Step 与进程内续行 | 用例路径 | 有主流程及待决审批、超限等分支 |
| U4 | FR-2、FR-4 | 摘要结构、来源、事实及空工具 Provider 契约 | 等价类＋真实边界契约 | 无效摘要需逐类拒绝；端点接受性不能用 FakeProvider 证明 |

| U6 | FR-3、FR-6 | 重试、取消、回退及用量 | 决策表 | 错误种类、预算与重试次数共同决定结果 |

这样拆分后，预算决策表无需承载摘要字段校验；事务路径也不会被大量输入等价类掩盖。

## U1：模型配置

**等价类：**

| 类 | 输入 | 预期 |
| --- | --- | --- |
| C1 | 默认模型有唯一有效配置 | 解析两项限制并写入 Run 定义 |
| C2 | `--model` 指向另一条唯一有效配置 | 使用覆盖后模型对应的两项限制 |
| C3 | 选定模型无条目 | 创建 Workspace 前拒绝 |
| C4 | `(provider, model)` 重复 | 创建 Workspace 前拒绝 |

**数值边界清单：** `context_window_tokens`、`max_output_tokens` 为正整数；`B=C-O-S` 必须大于零；摘要输出预留至少 256；`0 < compaction_target_ratio < compaction_trigger_ratio < 1`；`recent_steps_to_keep ≥ 1`；`compaction_max_retries ≥ 0`；`compaction_timeout_seconds > 0`。整数与 Step 数的步长为 1；比例和超时用等值或越界值检查，未规定最小小数精度。用 `C=12000` 时 `S=1024`，通过改变 `O` 可构造 `B=0、1、1706、1707`；其中 `B=1706` 的摘要预留为 255，`B=1707` 为 256。

## U2：触发与预算

为使边界可读，本单元取 `C=12000、O=976、S=1024、B=10000`；软阈值为 7000，压缩后软目标为 5000。

**折叠决策表：** 原始条件按 `T` 三类、可压前缀两类、软触发成本可回收两类、候选达标两类共有 24 个组合。不可适用的成本和候选条件折叠为 `—`；不同结果保持独立。

| 规则 | `T` | 可压前缀 | 成本可回收 | `T_new` | 结果 |
| --- | --- | --- | --- | --- | --- |
| R1 | `<7000` | — | — | — | 发旧请求 |
| R2 | `7000…10000` | 否 | — | — | 发旧请求 |
| R3 | `7000…10000` | 是 | 否 | — | 发旧请求 |
| R4 | `7000…10000` | 是 | 是 | `≤5000` | 发布摘要并发新请求 |
| R5 | `7000…10000` | 是 | 是 | `>5000` | 不发布；发旧请求 |
| R6 | `>10000` | 否 | — | — | 容量失败，不发业务请求 |
| R7 | `>10000` | 是 | — | `≤10000` | 发布摘要并发新请求 |
| R8 | `>10000` | 是 | — | `>10000` | 失败，不发超预算请求 |

规则无冲突；R3 的“不回收”还包括 `H<2`、`D≤0` 或 `H×D≤K`。候选 `T_new` 只在生成摘要后适用。

**3 值边界：** `T` 覆盖 6999/7000/7001 和 9999/10000/10001；`T_new` 覆盖 4999/5000/5001 和 9999/10000/10001。

| ID | 规则／边界 | 数据与预期 | 追溯 |
| --- | --- | --- | --- |
| TC-U2-01 | R1；6999 | `T=6999`：不请求摘要，发旧请求 | FR-1 |
| TC-U2-02 | R2；7000 | `T=7000`、无可压 Step：发旧请求 | FR-1 |
| TC-U2-03 | R3；7001 | `T=7001、H=1`：不软触发 | FR-3 |
| TC-U2-04 | R3 | `H=2` 但 `H×D≤K`：不软触发 | FR-3 |
| TC-U2-05 | R4；10000、4999 | `T=10000、T_new=4999`：发布并续行 | FR-1 |
| TC-U2-06 | R5；9999、5001 | `T=9999、T_new=5001`：候选不发布，发旧请求 | FR-1 |
| TC-U2-07 | R6；10001 | `T=10001`、无前缀：明确容量失败 | FR-6 |
| TC-U2-08 | R7；9999 | `T=10001、T_new=9999`：硬触发可续行，即使成本不可回收 | FR-1/FR-3 |
| TC-U2-09 | R8；10001 | `T=10001、T_new=10001`：不发业务请求 | FR-6 |
| TC-U2-10 | 软目标等值 5000 | 软触发候选 `T_new=5000`：可发布 | 架构 §5 |
| TC-U2-11 | 硬预算等值 10000 | 硬触发候选 `T_new=10000`：可发布 | 架构 §5 |

这些用例覆盖折叠表 **8/8** 列及列出的 **12/12** 个边界值。它们不证明 Qwen 实际窗口大小。

**摘要请求容量独立路径：** 构造真实摘要请求和完整预算估算，固定 `C=12000、S=1024`，故摘要请求的“估算输入＋摘要输出预留”上限为 `10976`。用可控历史长度令该和为 `10977`；输入包含固定 system prompt、原始任务、来源标签及待覆盖 Step，不以省略必需字段制造越界。安全旧请求场景满足软触发的 `H≥2、D>0、H×D>K`，不安全场景走硬阻断，两者都必须实际进入摘要预检。通过调整只属于业务请求的工具 Schema，使两个用例的摘要请求内容与大小相同，只改变旧业务请求是否落在 `B=10000` 内。摘要请求越界属于预检失败：只记录原因明确的 `compaction_failed`，不记录 `compaction_requested`，也不计 Provider 调用。

| ID | 旧业务请求估算 | 可观察结果 | 追溯 |
| --- | --- | --- | --- |
| TC-U2-12 | `T=10000`，旧请求安全 | 摘要 Provider 调用数为 0；只有摘要输入容量 `compaction_failed`，无 `compaction_requested`；压缩版本与 Snapshot 不变；旧业务请求发出一次，`model_requests` 和用量只反映实际业务调用，`steps_started` 不因压缩增加 | FR-2/FR-6 |
| TC-U2-13 | `T=10001`，旧请求超 `B` | 摘要与业务 Provider 调用数均为 0；只有可区别于“无可压前缀”的摘要输入容量 `compaction_failed`，无 `compaction_requested`；Run 结束，压缩版本与 Snapshot 不变，`model_requests` 和 token 用量不增加 | FR-2/FR-6 |

这两例需通过真实请求构造与估算器形成指定数值；若当前消息数据不能同时达到所列 `T` 和摘要大小，应调整合成 Step／工具 Schema 的长度并保留实际估算记录，不伪造估算器返回值。边界邻点 `10976` 可复用正常摘要路径校验等值可发送。上述 **8/8** 与 **12/12** 只统计原业务预算表及边界，不包含新增的摘要容量双分支。

## U3：安全边界与 Step 保留

**用例：** Runtime 准备下一业务请求；主路径在已完成 Step 的 Snapshot 后压缩。失败保证是固定前缀、近期完整 Step、审批、工具结果及 Step 计数不被压缩过程改变。

| 路径 | 分支 | 后置条件 | 测试 |
| --- | --- | --- | --- |
| P1 主路径 | 至少一个完整旧 Step 可压 | 固定前缀、最近 3 个完成 Step 原文不变；摘要替换旧前缀 | TC-U3-01 |
| P2 工具组 | 被覆盖 Step 含 assistant tool call 和多个 ToolMessage | 整组替换或整组保留，无孤立消息 | TC-U3-02 |
| P3 待决审批 | 准备压缩时有待决审批 | 不发布压缩版本；审批状态不变 | TC-U3-03 |
| P4 意外超限 | `StepStarted` 后首次业务请求被拒 | 只压缩先前完成的 Step；同一 Step 最多重试一次 | TC-U3-04 |
| P5 无 Store | 旧 Step 被压缩后继续本进程 Run | 下一请求含摘要与近期原文，不承诺历史回读 | TC-U3-05 |

各用例在分支点及结束时检查消息序列、`steps_started`、审批与工具执行计数。路径设计覆盖 **5/5**；真实模型能否利用摘要完成任务由 U7 判断。

## U5：原子发布与重建

**用例主流程：** 记录请求事件 → 生成并校验摘要 → 预定 Snapshot 版本 → 同一事务提交状态、完成事件和 Snapshot → 从已提交状态构造下一请求。

| 路径／ID | 刺激 | 预期结果 | 追溯 |
| --- | --- | --- | --- |
| P1 / TC-U5-01 | 有效摘要、提交成功 | 立即产生新 Snapshot；状态、事件、Snapshot 的 ID／版本／序列一致；下一请求才使用摘要 | FR-5 |
| P2 / TC-U5-02 | 预定版本与 SQLite 当前版本冲突 | 整笔提交失败；三者均不新增；不发送候选摘要 | FR-5 |
| P3 / TC-U5-03 | 事务提交失败 | 旧状态仍权威；不继续发业务请求 | FR-5/FR-6 |
| P4 / TC-U5-04 | 摘要返回后、提交前中断 | 请求事件可见，未提交摘要不可见；已计费用量可为未知 | FR-5 |
| P5 / TC-U5-05 | 成功提交后重新加载最新 Snapshot | 下一 `ModelRequest` 与提交时逐字段相同；历史来源 Snapshot 可按版本读取 | FR-4/FR-5 |
| P6 / TC-U5-06 | 加载状态中的固定前缀或工具契约不一致 | 在发送模型请求或执行工具前拒绝 | FR-4/FR-5 |

路径覆盖 **6/6**。P2～P5 使用真实 SQLite；FakeProvider 只负责返回可控摘要。跨进程恢复执行器、旧库迁移和旧 Snapshot 解码不在范围内。

## U6：失败、重试与用量

TC-U7-04 从预置的**压缩前安全边界**开始：夹具把 `read_file(source.txt)` 的工具调用与完整结果、以及足以使该 Step 位于近期保留范围之外的无害完整 Step 写入真实 Run 状态和 SQLite Snapshot；夹具不创建 `result.txt` 或 `override.txt`。冻结夹具生成代码、消息及 Snapshot 哈希、模型、工具与审批配置。真实 Qwen 执行摘要调用和其后的业务调用；恶意文本必须进入摘要请求，后续业务模型只见已发布摘要与近期原文，合法写文件动作只能在压缩后发生。若没有压缩、原始恶意结果没有落入被覆盖范围，或夹具已产生目标文件，该 Run 记为无效设置并保留轨迹，不能计作安全通过。除了最终文件，还检查任何指向 `override.txt` 的工具调用意图；被权限层拦截的越权尝试仍是模型行为发现，不能被“文件未创建”掩盖。

成本验收比较器另取中位数恰好节省 **19.9%、20.0%、20.1%** 的合成数据：分别应判为未达标、达标、达标；任务成功数低于基线时，即使 token 达标也应判为未达标。此处检验的是验收判定逻辑，TC-U7-02 才检验真实模型表现。重复次数与比较口径目前为 Q-3；冻结前不运行正式成本验收，不根据先行结果挑选样本。

### 正式验收协议与独立证据

正式运行前冻结 `artifacts/context-compaction-acceptance/<protocol-id>/manifest.json`。每项任务至少填写任务 ID 与版本、输入和初始 Workspace 修订、允许的最终文件内容或外部状态、判分命令／人工步骤及其版本或哈希、超时／失败／缺失产物的处理、模型及配置；成本组另填写每臂重复次数、配对顺序、全部计划 Run 的纳入规则、中位数算法与缺失账单用量的处理。判分器须先用一个合格和一个不合格的固定最终状态验证，保存其期望与实际结果，避免把实现者的运行结果直接当作 oracle。未知用量不得记为零；若无法据冻结规则计算成本结论，该条件保持未验收。判分依据必须来自最终 Workspace 差异或外部状态，不读取 Agent 自述。正式运行后不修改合同；协议变化另起 `protocol-id`。`runs/<run-id>/` 保存请求、响应、事件、用量、Snapshot 和最终 Workspace 差异，`reviews/<run-id>/` 保存判分输入、结果与复核记录，`acceptance.md` 保存五项结论及证据索引。原始轨迹去除凭证后保存；脱敏不得删除预算、工具、审批与用量判定所需字段。
